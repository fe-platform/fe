## Core Concepts

### Import Specifiers

All MFE and platform imports use the `fe:` URI scheme:

```
fe:@org/mfe-name          → MFE entry point
fe:@org/mfe-name/subpath  → Deep import (exports field)
fe:state                  → Platform: state management
fe:visuals                → Platform: UI kit
fe:net                    → Platform: API layer
```

Resolution is handled by browser-native import maps generated by the platform.

### Composition Model

The shell is itself an MFE. It imports and renders other MFEs. There is no special mounting API—an MFE exports components, the shell imports and renders them.

```
Shell (fe:@platform/shell)
  └── imports fe:@org/header
  └── imports fe:@org/main-content
  └── imports fe:@org/footer
```

Nested composition follows the same pattern. Any MFE can import any other MFE.

### Source Publishing

Teams publish TypeScript source to a central registry. The platform build server:
1. Resolves dependencies
2. Bundles with current browser targets
3. Generates import map entries
4. Extracts and stores import metadata
5. Deploys artifacts to CDN

This enables platform-wide upgrades (externalized libs, browser support, optimizations) without team redeployment.

### Import Metadata

Each MFE declares metadata for its imports:

```json
{
  "fe:@org/checkout": {
    "modulepreload": ["./chunk-abc.js", "./chunk-def.js"],
    "preload": [
      { "href": "./styles.css", "as": "style" },
      { "href": "./hero.webp", "as": "image" }
    ],
    "prefetch": ["https://api.example.com/cart/warmup"]
  }
}
```

The platform uses this metadata to eliminate network waterfalls.

### Preload Injection

**Static imports** — Platform extracts at build time, generates `<link rel="modulepreload">` tags in HTML for the entry route.

**Dynamic imports** — Build rewrites to inject preloading:

```js
// Authored
const Checkout = await import("fe:@org/checkout")

// Rewritten
const Checkout = await (
  __fePreload("fe:@org/checkout"),
  import("fe:@org/checkout")
)
```

`__fePreload` is a platform-injected runtime (~20 lines) that appends link tags based on the metadata manifest. Non-blocking.

### State Management

Single global Zustand store on the main thread. MFEs access state via `fe:state`:

```js
import { useStore, getStore } from "fe:state"
```

No worker threads. No message passing between MFEs.

### State Ownership & Mutation Rules

A single global store requires strict ownership.

**Invariants:**
1. Every state slice has exactly one owner (platform package or MFE)
2. Only the owner may write to its slice
3. All others are read-only unless explicitly delegated

**Naming convention (required):**

```
<owner>/<slice>

platform/auth
platform/routing
workflows/list
checkout/cart
```

**Enforcement:**
- Build-time validation checks declared ownership vs usage
- Runtime enforcement blocks unauthorized writes (permissions-backed)
- Read access governed by `permissions.state.read`

### MFE Failure & Isolation Model

Failures are inevitable; blast radius is not.

**Failure classes:**

| Failure | Behavior | Scope |
|---------|----------|-------|
| Import failure | Shell renders declared fallback | Isolated to MFE |
| Runtime exception | Shell error boundary catches | Isolated to MFE |
| Preload failure | Ignored (non-blocking) | None |
| Repeated failures | Optional auto-disable via rollout config | MFE-level |

**Rules:**
- An MFE must never prevent the shell from rendering
- All MFEs are wrapped in a platform-provided error boundary
- MFEs may declare an optional `fallback` export; otherwise shell default is used
- Failure telemetry is automatic and attributed to the MFE

```tsx
// Shell composition (conceptual)
<ShellSlot mfe="fe:@org/checkout" fallback={<CheckoutUnavailable />} />
```

### CSS Isolation Model

**Default:** Build-time scoped CSS (hashed class names). No runtime style rewriting. No Shadow DOM.

**Exceptions:**
- `fe:visuals` and the shell may emit global styles
- MFEs may opt-in to global styles explicitly in manifest:

```json
{
  "style": {
    "scope": "global"
  }
}
```

**Rationale:** Predictable output. Tooling-friendly. No cross-MFE bleed by default. No Shadow DOM edge cases (portals, theming, a11y).

### Deep Imports

MFEs declare public subpaths via `exports` in their manifest:

```json
{
  "name": "@org/checkout",
  "exports": {
    ".": "./src/index.ts",
    "./components": "./src/components/index.ts",
    "./hooks": "./src/hooks/index.ts"
  }
}
```

Platform generates corresponding import map entries:

```json
{
  "imports": {
    "fe:@org/checkout": "https://cdn.../checkout/index.js",
    "fe:@org/checkout/components": "https://cdn.../checkout/components.js",
    "fe:@org/checkout/hooks": "https://cdn.../checkout/hooks.js"
  }
}
```
